# Corporation / Cyber-Cop: правила разработки

## Начало и возобновление
1. Сначала прочитать `DEVELOPMENT_STATE.md`, затем `docs/reverse-engineering/README.md` и тематический документ. Проверить фактический HEAD ветки `wip` и незакоммиченные изменения.
2. До дизассемблирования искать адрес/символ через `rg` в исходниках, `symbols.json`, реестре адресов и исследованиях. Не разбирать весь ROM для известной процедуры. Если сведений нет, исследовать минимальный нужный диапазон и сохранить вывод.
3. Адрес имеет смысл только вместе с платформой, сборкой и контрольной суммой. Новые адреса патчей брать из таблицы символов нужной сборки, не из памяти чата.

## Ветки и сохранение
- Рабочая ветка — `wip`. Не менять, не сливать и не публиковать в `main` без отдельного прямого указания пользователя. Не делать force push, не переписывать чужую историю.
- Завершённое проверенное исправление: один тематический коммит `fix: ...` с изменёнными исходниками, необходимой документацией и результатом проверки. Не повторять весь анализ ради коммита.
- Долгое исправление: после значимого промежуточного результата, перед дорогим экспериментом, перед завершением хода и ориентировочно раз в 20–30 минут активной работы сохранять `WIP (unverified): ...`. Это ориентир, не фоновый таймер. Не ждать исчерпания лимита: его момент заранее неизвестен.
- Коммит должен быть отправлен на GitHub и подтверждён чтением HEAD. Локальный коммит ещё не удалённая резервная копия. Если push недоступен, явно записать это и сохранить исходники отдельно, не заявляя об успешной синхронизации.
- Удалённое изменение через GitHub API: сначала проверить предлагаемые файлы `tools/check_publication.py`, создать дерево от актуального дерева `wip`, затем обновить только `wip` с expected_sha. При конфликте перечитать HEAD и сохранить чужие изменения.
- Не придумывать прошлую историю отдельных исправлений. Первая загрузка v36 — честный общий checkpoint test02; дальнейшие изменения сохранять по отдельности.

## Постоянная память проекта
- Вместе с исправлением обновлять `DEVELOPMENT_STATE.md`: задача, изменения, проверки с датой/средой, оставшиеся шаги, риски, рабочая база и проверенный checkpoint.
- В документации помечать CONFIRMED / HYPOTHESIS / OPEN / SUPERSEDED. Для подтверждения указывать исходник, тест или наблюдение; не превращать предположение в факт.
- Ссылаться на ранее выполненную проверку и её fingerprint. Повторять тест при изменении относящегося к нему кода/данных, провале или конкретной неразрешённой неопределённости.
- SHA коммита не может ссылаться сам на себя внутри своего содержимого. Точный SHA проверенного checkpoint записывать последующим небольшим docs-коммитом; не создавать бесконечную цепочку обновлений.

## Публикация
- Не отправлять ROM (оригинальные и модифицированные), образы дискет, savestate, SRAM, временные дампы, полные дизассемблированные листинги, извлечённые графику/звук/карты или их текстовые/base64-копии.
- Публиковать авторский код патча/экстрактора, адреса, объяснения, проверки и хеши. Игровые входы предоставляются локально владельцем.
- Использовать явный список изменённых файлов, не `git add .`. Прежде чем писать на GitHub, просмотреть diff и запустить проверку публикации. `.gitignore` и hook — вспомогательные барьеры, не доказательство прав на содержимое.
- Существующие опубликованные материалы не удалять и историю не переписывать без задания на это. Новые исключения для публикации ресурсов не вводить автоматически.
- Пакет `v36/package.py` из исследовательского workspace НЕ пригоден для GitHub: он включает ROM и приватные материалы. На GitHub этот упаковщик не публикуется.

## Завершение
Кратко сообщить, что сделано, что проверено, что осталось неизвестным, ссылку на `wip`/коммит. Не выдавать WIP за проверенный релиз. Результаты test02 ещё ожидают игрового теста пользователя.
